3換一種投影方式，會不會變成另一個形狀

使用者發言的五種顏色🟢 請求動作🔵 問問題🟣 關鍵決策 / 概念提問🟡 中斷 / 踩剎車🔴 設計回饋 / 要求自我審視（「有沒有哪一顆不對勁？說明你為什麼這樣覺得」）。完整說明 →
🟣 使用者：同一顆神經元，換一種投影方式看起來會不會像是不同的形狀？如果會，那代表什麼。

這是整集最好的一句話。它不要求做事，要求的是理解。答案要分成兩層：

換算符：形狀不會變
MIP 與 mean 的非零像素集合逐位相同。任何逐射線的算符都不能改變輪廓，只能改變哪些構造搶眼。
換方向：會變成另一個東西
同一組體素，只換觀看角度，可見像素數就差 1.5 倍，而且結構的「長相」整個改變。

0° 的「實心扇形」其實是一片彎曲的薄殼——扇形只是薄殼正對鏡頭時的假象。可見像素數也跟著跑：18° 是 34,747，90° 只剩 23,186，差 1.5 倍。同一顆神經元的「面積」不是不變量。

「操作原理」（四個欄位，點一下展開）——不寫程式的話整段可以跳過。

操作原理 · method

M-13點雲旋轉投影，不要內插整個立方體

把非零體素抽成 (座標, 強度) 的點清單，繞 y 軸旋轉座標，再打點取最大值。

斜角投影有兩種做法。標準做法是把整個立方體做仿射變換＋三線性內插，成本是 O(nx·ny·nz)；點雲做法只處理有訊號的體素，成本是 O(非零數)。這批資料只有 0.85% 非零，所以點雲快兩個數量級。繞 y 軸轉只影響螢幕橫座標，縱座標永遠是 y——所以六個畫格自動對齊。

sx = ((x - cx) * cos(t) + (z - cz) * sin(t)) + (W - 1) / 2
sy = (y - cy) + (H - 1) / 2
← 可左右滑動 →

畫布寬度取 round(hypot(nx, nz))：神經元轉一圈掃過的直徑就是 x-z 對角線，取這麼寬，畫格之間才不會忽大忽小地抖。

zz, yy, xx = np.nonzero(vol)
values = vol[zz, yy, xx]
centre = ((nx - 1) / 2, (ny - 1) / 2, (nz - 1) / 2)
W, H = int(round(math.hypot(nx, nz))), ny
← 可左右滑動 →

中心必須是 (n - 1) / 2 不是 n / 2——索引從 0 數到 n−1，中點在 (n−1)/2。這個半格的差，加上取整規則，正是下面 M-15 那個 bug 的來源。稀疏度高才划算：如果非零比例超過一成左右，點雲反而慢。

M-14用排序做 max-scatter

把幾萬個點打到二維畫格上，同一格取最大值——不用 Python 迴圈。

numpy 沒有內建的 max-scatter（img[idx] = val 是後寫贏，不是取最大）。技巧是把「像素編號」與「值」打包成一個整數鍵：key = 像素編號 × 65536 + 值。排序之後同一個像素的所有點會連在一起，而且值由小到大——所以每一段的最後一筆就是該像素的最大值。找分段邊界只要比較相鄰元素的像素編號。整個過程是一次排序，O(n log n)，全向量化。

key = (iy * W + ix).astype(np.int64) * 65536 + vals.astype(np.int64)
key.sort()
pix, val = key >> 16, key & 0xFFFF
last = np.empty(pix.size, dtype=bool); last[-1] = True
np.not_equal(pix[1:], pix[:-1], out=last[:-1])   # 每段的最後一筆
img = np.zeros(H * W); img[pix[last]] = val[last]
← 可左右滑動 →

65536 這個乘數綁死了「值必須放得進 16 位元」。ushort 剛好可以，但換成 float 或更大的整數就會壞掉，而且不會報錯，只會給出錯的圖。用之前先 assert vals.max() < 65536。另外 .astype(np.int64) 不能省，不然乘 65536 會溢位。

投影造成的假接合可以直接量：沿射線數不連續的段數，≥2 段代表 3D 上分開的構造被畫成同一個像素。

M-17量投影造成的假接合

沿每條射線數「不連續的段數」，≥2 段代表 3D 上分開的構造被畫成同一個像素。

把布林體積沿投影軸移到最後一維，對最後一維做差分，由 0 變 1 的次數就是段數（prepend=0 讓射線開頭的訊號也算一段）。這把「這兩根突起有沒有相接」從肉眼判斷變成一個比例。實測：

視角≥2 段的可見像素比例最多幾段
正視32.9%11
側視77.8%22
俯視70.7%23

側視圖有近八成的可見像素，其射線上其實有兩段以上分離的構造。只看一張投影就判斷連通性，這個比例的像素都不能信。

m = np.moveaxis(vol > 0, axis, -1)
runs = (np.diff(m.astype(np.int8), axis=-1, prepend=0) == 1).sum(axis=-1)
print(100 * (runs >= 2).sum() / (vol.max(axis=axis) > 0).sum())
← 可左右滑動 →

prepend=0 不能省，不然射線一開頭就有訊號的那一段會被漏掉。分母要用可見像素數（pmax > 0）而不是整個平面的像素數——背景像素本來就是 0 段，算進去會把比例稀釋掉。

🐛 AI 的第二個錯：np.rint 的「四捨六入五成雙」

斜角投影改用點雲打點實作。第一版在 0° 時只得到 9,828 個可見像素——但 0° 應該完全等於軸對齊的正視圖，正確答案是 31,089。

sx = (x - cx) + W/2        # 中心是 (n-1)/2，這裡用 W/2 → 差半格
ix = np.rint(sx)            # rint 是四捨六入五成雙

rint(22.5) = 22   rint(23.5) = 24   rint(24.5) = 24
# → 相鄰兩個整數座標被併進同一格，兩軸各掉一半解析度
← 可左右滑動 →

這個 bug 修了兩次才對：

第一修改成 (W-1)/20° 對了（31,089），但 90° 又錯——11,967，正確是 23,186。換成 z 軸的奇偶性相撞，同一個病。
第二修改用 floor(s+0.5)不依賴取整規則的奇偶行為，兩個角度都對。
這個 bug 抓得到，唯一的原因是有一個已知的正確答案：0° 的斜角投影必須等於軸對齊的正視圖。沒有這個對照，圖看起來一樣漂亮，只是細節少了一半，而且不會有人發現。

M-15取整：floor(s+0.5)，不要用 np.rint

把浮點的螢幕座標轉成整數格號。用 np.floor(s + 0.5)，不要用 np.rint。

np.rint 是 IEEE 754 的預設模式「四捨六入五成雙」（banker's rounding）：遇到剛好 .5 時進到最接近的偶數。所以 rint(22.5)=22、rint(23.5)=24、rint(24.5)=24——相鄰兩個整數座標被併進同一格。只要平移量剛好落在半格（畫布寬度與體積中心的奇偶性一撞就會發生），整張圖等於兩軸各掉一半解析度。floor(s + 0.5) 一律往上取，不依賴奇偶性，兩個角度都對。

ix = np.floor(sx + 0.5).astype(np.int32)   # 不要用 np.rint
iy = np.floor(sy + 0.5).astype(np.int32)
← 可左右滑動 →

這個 bug 修了兩次才對。第一修把偏移從 W/2 改成 (W-1)/2，0° 對了（31,089），但 90° 又錯——換成 z 軸的奇偶性相撞，同一個病。第二修才改用 floor(s+0.5)，不依賴取整規則的奇偶行為，兩個角度都對。修好一個角度不代表修好了：換一組參數再驗一次。附帶發現：另一個既有專案（fly_neuron/Visualization/render_rotation.py）用的是同一條 W/2 + np.rint 公式，那邊因為縮放係數一律小於 1、座標本來就非整數，沒有系統性併格，影響不明顯——但公式本身有同樣的脆弱點。沒有動那個檔案，只把發現記錄下來。

M-16用已知的正確答案對照

0° 的斜角投影必須完全等於軸對齊的正視圖。拿這個當測試。

這是這一集最重要的方法論。斜角投影在 0° 時，旋轉矩陣是單位矩陣，所以結果必須跟 vol.max(axis=0) 逐像素相同——一個你事先就知道答案的測試（ground truth）。沒有這個對照，第一版得到 9,828 個可見像素而正確答案是 31,089，只剩 32%——而圖看起來一樣漂亮，只是細節少了一半，不會有人發現。

角度精確值（軸對齊）當初的寫法只剩修正後比對
0°31,0899,82832%31,089相符
90°23,18611,96752%23,186相符
exact = int((vol.max(axis=0) > 0).sum())          # 軸對齊的正視圖
got   = int((splat_mip(pts, vals, 0, c, size) > 0).sum())
assert got == exact, f'0° 應為 {exact}，實得 {got}'

「圖看起來對」不是驗證。 這一集四個錯裡有兩個是靠對照抓到的（另一個是把碎片畫出來看位置，見 M-26）。找對照的訣竅是：同一件事用兩種方法算，結果要一樣。0° 與 90° 剛好都有軸對齊的版本可以對，就用它們。

附帶發現：另一個既有專案（fly_neuron/Visualization/render_rotation.py）用的是同一條 W/2 + np.rint 公式。那邊因為縮放係數一律小於 1、座標本來就非整數，沒有系統性併格，影響不明顯——但公式本身有同樣的脆弱點。沒有動那個檔案，只把發現記錄下來。
