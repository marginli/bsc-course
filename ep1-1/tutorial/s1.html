1開場：先不要寫程式

使用者發言的五種顏色🟢 請求動作🔵 問問題🟣 關鍵決策🟡 中斷 / 踩剎車🔴 設計回饋 / 糾錯完整說明 →
🔵 使用者：neuron_20/ 資料夾裡有 20 個我打不開的檔案。先不要寫任何處理程式，你先告訴我它們是什麼格式，以及你是怎麼判斷出來的。

這句話裡有三個指令，缺一不可：（1）判斷格式、（2）說明判斷方法、（3）先不要動手寫程式。第三點是 🟡 踩剎車——它擋掉了 AI 最常見的失敗模式：還沒搞懂資料就開始寫轉檔程式。

AI 做了什麼先 ls 看檔名與大小，再跑 file 指令——結果只回報 data，表示系統的格式資料庫裡沒有這個格式。於是改用最原始的方法：把檔案前 1200 個位元組直接印出來看。

下面的「操作原理」是給想自己動手寫程式的人看的，四個欄位預設收著；整段跳過不影響後面的閱讀。

操作原理 · method

M-01列出檔名與大小

取得 20 個檔的檔名與位元組數，還沒有讀任何內容。

檔案大小、時間、權限存在檔案系統的 inode（Windows 上是 MFT 記錄）裡，跟檔案內容分開存放。所以問大小是 O(1) 的中繼資料查詢，不需要把檔案讀過一遍。這也是為什麼幾 GB 的檔案 ls 一樣是瞬間回應。

from pathlib import Path
for f in sorted(Path('neuron_20').glob('*.am')):
    print(f.name, f.stat().st_size)   # st_size 來自 inode，不讀內容
← 可左右滑動 →

檔名本身是線索但不是證據。副檔名 .am 只是宣稱（見 〈前置知識〉1-1）；大小相近只能說明它們可能是同一類東西，不能拿來判定格式。

M-02跑 file 指令，得到 data

用作業系統內建的格式辨識工具問一次，結果是 data——意思是「不認得」。

file 指令背後是 libmagic，它有一份 magic 資料庫：每一條規則說「在 offset X 有位元組序列 Y，就是格式 Z」。它做的是特徵比對，不是理解檔案。資料庫收了上千種格式，但 AmiraMesh 這種學術／商業軟體的原生格式不在裡面，所有規則都比不中，於是回落到最後一條：data（不明的二進位資料）。

$ file neuron_20/*.am        # 回報 data 就是「我的資料庫裡沒有」
$ file --mime-type x.am      # 只要 MIME 類型
$ man 5 magic                # magic 規則的寫法，可以自己加一條
← 可左右滑動 →

「file 說 data」不等於「這個檔壞了」，只等於「這台電腦的資料庫沒收錄」。反過來也一樣：file 認得的答案也可能是誤判——它只看了幾個位元組。把 file 當成第一個提示，不是結論。

M-03把前 1200 個位元組直接印出來

十六進位傾印（hex dump）：把檔案開頭的每個位元組同時用十六進位與可列印字元印出來。

任何檔案都是位元組序列，每個位元組是 0–255 的整數。傾印工具做兩件事：把整數印成兩位十六進位（0–255 剛好對應 00–ff，一個位元組一定是兩個字），以及把落在可列印 ASCII 範圍（0x20–0x7e）的位元組同時印出對應字元、其餘印成點。人靠右邊那一欄一眼看出這段是文字還是亂碼——這就是「文字或二進位」最原始的判別法。

$ od -A d -t x1z -N 1200 x.am     # -A d 位址用十進位，方便對照 offset
$ xxd -l 1200 x.am                # 或用 xxd，輸出更好讀
b = open('x.am','rb').read(1200)
print(b.decode('latin-1'))        # latin-1 不會丟例外，任何位元組都對得到字元
← 可左右滑動 →

用 utf-8 解碼二進位檔會直接拋例外，看不到東西。判讀階段一律用 latin-1 或 errors='replace'，先看見再說。另外別一次印整個檔——760 KB 的傾印沒有人讀得完，開頭幾百到幾千個位元組就夠了。

操作原理 · method

M-04認出這是「純文字檔頭 + 二進位酬載」

看懂檔案的結構是：一段人類可讀的文字說明書，接著一個標記，然後是壓縮過的影像資料。

這是很常見的一種格式設計。文字檔頭的好處是自我描述：不需要任何專用工具，任何人拿記事本或 od 就能知道裡面裝什麼、多大、怎麼讀。代價是解析要靠字串處理、檔頭長度不固定。與它相對的是純二進位檔頭（固定欄位、固定位址，讀起來快但完全不可讀）。AmiraMesh 選了前者，本案能被判讀出來，一大半是因為這個設計決定。

本案的檔頭有三個關鍵宣告：

宣告意思後面哪一步會用到
# AmiraMesh BINARY-LITTLE-ENDIAN 2.1格式與端序M-26 解讀 ushort 時要知道端序
define Lattice 153 347 161三個方向各有幾個體素M-06 尺寸恆等式、M-12 體素尺寸
Lattice { ushort Data } @1(HxZip,760523)型別、資料段編號、壓縮方式與壓縮後長度M-22 核對長度、M-26 解讀型別

檔頭寫的是宣稱，不是實測（見 〈前置知識〉1-2）。這一集最後的反轉就出在這裡：20 個檔都宣稱 ushort，實際值域卻分兩群。

AI 做了什麼比對 20 個檔的第一行全部相同；再檢查 @1 之後的資料開頭是 78 9c（zlib 的招牌位元組）；最後真的解壓一次，得到 17,095,302 位元組，正好等於 153 × 347 × 161 × 2——維度與「每體素 2 位元組」完全吻合。判定完成。

操作原理 · method

M-05認出資料段開頭的 78 9c 是 zlib

在資料段起點取兩個位元組，判斷這是不是 zlib 壓縮串流。

zlib 串流的前兩個位元組是固定結構的標頭（RFC 1950 §2.2），不是隨機的資料。它由 CMF 與 FLG 兩個位元組組成，而且規格要求 (CMF×256 + FLG) 必須被 31 整除——這是一個內建的檢查碼。所以看到 78 9c 不只是「看起來像」，而是可以驗算的：0x789c = 30876 = 31 × 996。隨便兩個位元組能通過這個檢查的機率只有 1/31。位元的完整拆解見 M-08。

i = b.find(b'\n@1\n') + 4          # 資料段起點：用標記找，不要硬編碼
cmf, flg = b[i], b[i+1]
assert cmf & 0x0f == 8              # CM=8 → deflate
assert (cmf*256 + flg) % 31 == 0    # RFC 1950 的 31 整除檢查
← 可左右滑動 →

不要只比對「78 9c」這個組合。9c 編碼的是壓縮等級，換個等級就變成 78 01、78 5e、78 da——同樣是合法 zlib。穩健的判斷是「CM 等於 8」加上「31 整除」，而不是死記某一對位元組。

M-06真的解壓一次，用尺寸恆等式驗證

把資料段丟進 zlib 解壓，量解壓後的位元組數，跟檔頭宣告的維度相乘比對。

這是整個判讀的收尾，也是端到端驗證的典型長相。恆等式是：

解壓後位元組數  ==  d1 × d2 × d3 × (每個體素的位元組數)
17,095,302     ==  153 × 347 × 161 × 2
← 可左右滑動 →

這條式子一次同時驗了四件獨立的事：資料段起點找對了（不然解不開）、這確實是 zlib（不然解不開）、檔頭宣告的維度是真的、以及 ushort 等於 2 個位元組。任何一項猜錯，等號都不會成立。用一個容易量的量去交叉檢查一串假設，是判讀未知格式最有效的手法。

這條式子對三個維度的任何排列都成立——153×347×161 和 161×153×347 乘起來一樣大。所以它證明得了「維度是這三個數」，證明不了「哪個數對應哪個軸」。教學網頁「還沒做的事」講的就是這件事，細節見 M-27。驗證通過只代表假設沒被推翻，不代表它是唯一解。

注意 AI 這裡沒有違反「不要寫處理程式」：它只做了判讀（看位元組、驗證一次解壓），沒有產生任何轉檔或處理輸出。「不要寫程式」限制的是產出，不是限制動腦。
