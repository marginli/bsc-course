判讀未知格式的 6 個核心觀念

手上有一批打不開的檔案時，先記住這 6 件事：

  1. 先判讀，再寫程式。不知道是什麼就開始寫轉檔程式，等於用猜的蓋房子。這一集使用者第一句話就是「先不要寫任何處理程式」——這句話決定了整段品質。
  2. 檔案自己會說話。大多數格式的開頭就寫著自己是誰。file 指令沒用時，直接把前幾百個位元組印出來看。
  3. 要求證據能追到位元組。「我覺得這是 X 格式」和「offset 438 的兩個位元組是 78 9c，對應 RFC 1950 §2.2」是完全不同等級的回答。
  4. 查不到規格就說查不到。不是每個格式都有公開規格。分清楚「有規格佐證」「靠社群文件」「純屬推論」，比假裝都很確定有用得多。
  5. 動原始資料前先備份。研究資料常常是重跑不回來的。備份很便宜，重採樣很貴。
  6. 差異先列出來，不要急著抹平。看起來「只是格式不一致」的東西，可能是資料來源不同的唯一線索——這一集最後就是這樣打臉的。
💡 這一集完全沒有用到 git（版本控制），備份是用最土的方法（複製一份資料夾）。對初學者：先養成「動手前留退路」的習慣，工具用哪個都行。

PART 1完整對話時序

以下是這次協作的每一輪，依實際發生順序排列。使用者總共只講了 7 句話。

1開場：先不要寫程式

🔵🟡 使用者：neuron_20/ 資料夾裡有 20 個我打不開的檔案。先不要寫任何處理程式，你先告訴我它們是什麼格式，以及你是怎麼判斷出來的。

這句話裡有三個指令，缺一不可：（1）判斷格式、（2）說明判斷方法、（3）先不要動手寫程式。第三點是 🟡 踩剎車——它擋掉了 AI 最常見的失敗模式：還沒搞懂資料就開始寫轉檔程式。

AI 做了什麼先 ls 看檔名與大小，再跑 file 指令——結果只回報 data，表示系統的格式資料庫裡沒有這個格式。於是改用最原始的方法：把檔案前 1200 個位元組直接印出來看。

操作原理 · method

M-01列出檔名與大小

取得 20 個檔的檔名與位元組數，還沒有讀任何內容。

檔案大小、時間、權限存在檔案系統的 inode（Windows 上是 MFT 記錄）裡，跟檔案內容分開存放。所以問大小是 O(1) 的中繼資料查詢，不需要把檔案讀過一遍。這也是為什麼幾 GB 的檔案 ls 一樣是瞬間回應。

from pathlib import Path
for f in sorted(Path('neuron_20').glob('*.am')):
    print(f.name, f.stat().st_size)   # st_size 來自 inode，不讀內容

檔名本身是線索但不是證據。副檔名 .am 只是宣稱（見 prelim.docx 1-1）；大小相近只能說明它們可能是同一類東西，不能拿來判定格式。

M-02跑 file 指令，得到 data

用作業系統內建的格式辨識工具問一次，結果是 data——意思是「不認得」。

file 指令背後是 libmagic，它有一份 magic 資料庫：每一條規則說「在 offset X 有位元組序列 Y，就是格式 Z」。它做的是特徵比對，不是理解檔案。資料庫收了上千種格式，但 AmiraMesh 這種學術／商業軟體的原生格式不在裡面，所有規則都比不中，於是回落到最後一條：data（不明的二進位資料）。

$ file neuron_20/*.am        # 回報 data 就是「我的資料庫裡沒有」
$ file --mime-type x.am      # 只要 MIME 類型
$ man 5 magic                # magic 規則的寫法，可以自己加一條

「file 說 data」不等於「這個檔壞了」，只等於「這台電腦的資料庫沒收錄」。反過來也一樣：file 認得的答案也可能是誤判——它只看了幾個位元組。把 file 當成第一個提示，不是結論。

M-03把前 1200 個位元組直接印出來

十六進位傾印（hex dump）：把檔案開頭的每個位元組同時用十六進位與可列印字元印出來。

任何檔案都是位元組序列，每個位元組是 0–255 的整數。傾印工具做兩件事：把整數印成兩位十六進位（0–255 剛好對應 00–ff，一個位元組一定是兩個字），以及把落在可列印 ASCII 範圍（0x20–0x7e）的位元組同時印出對應字元、其餘印成點。人靠右邊那一欄一眼看出這段是文字還是亂碼——這就是「文字或二進位」最原始的判別法。

$ od -A d -t x1z -N 1200 x.am     # -A d 位址用十進位，方便對照 offset
$ xxd -l 1200 x.am                # 或用 xxd，輸出更好讀
b = open('x.am','rb').read(1200)
print(b.decode('latin-1'))        # latin-1 不會丟例外，任何位元組都對得到字元

用 utf-8 解碼二進位檔會直接拋例外，看不到東西。判讀階段一律用 latin-1 或 errors='replace'，先看見再說。另外別一次印整個檔——760 KB 的傾印沒有人讀得完，開頭幾百到幾千個位元組就夠了。

操作原理 · method

M-04認出這是「純文字檔頭 + 二進位酬載」

看懂檔案的結構是：一段人類可讀的文字說明書，接著一個標記，然後是壓縮過的影像資料。

這是很常見的一種格式設計。文字檔頭的好處是自我描述：不需要任何專用工具，任何人拿記事本或 od 就能知道裡面裝什麼、多大、怎麼讀。代價是解析要靠字串處理、檔頭長度不固定。與它相對的是純二進位檔頭（固定欄位、固定位址，讀起來快但完全不可讀）。AmiraMesh 選了前者，本案能被判讀出來，一大半是因為這個設計決定。

AI 做了什麼比對 20 個檔的第一行全部相同；再檢查 @1 之後的資料開頭是 78 9c（zlib 的招牌位元組）；最後真的解壓一次，得到 17,095,302 位元組，正好等於 153 × 347 × 161 × 2——維度與「每體素 2 位元組」完全吻合。判定完成。

操作原理 · method

M-05認出資料段開頭的 78 9c 是 zlib

在資料段起點取兩個位元組，判斷這是不是 zlib 壓縮串流。

zlib 串流的前兩個位元組是固定結構的標頭（RFC 1950 §2.2），不是隨機的資料。它由 CMF 與 FLG 兩個位元組組成，而且規格要求 (CMF×256 + FLG) 必須被 31 整除——這是一個內建的檢查碼。所以看到 78 9c 不只是「看起來像」，而是可以驗算的：0x789c = 30876 = 31 × 996。隨便兩個位元組能通過這個檢查的機率只有 1/31。位元的完整拆解見 M-08。

i = b.find(b'\n@1\n') + 4          # 資料段起點：用標記找，不要硬編碼
cmf, flg = b[i], b[i+1]
assert cmf & 0x0f == 8              # CM=8 → deflate
assert (cmf*256 + flg) % 31 == 0    # RFC 1950 的 31 整除檢查

不要只比對「78 9c」這個組合。9c 編碼的是壓縮等級，換個等級就變成 78 01、78 5e、78 da——同樣是合法 zlib。穩健的判斷是「CM 等於 8」加上「31 整除」，而不是死記某一對位元組。

M-06真的解壓一次，用尺寸恆等式驗證

把資料段丟進 zlib 解壓，量解壓後的位元組數，跟檔頭宣告的維度相乘比對。

這是整個判讀的收尾，也是端到端驗證的典型長相。恆等式是：

解壓後位元組數  ==  d1 × d2 × d3 × (每個體素的位元組數)
17,095,302     ==  153 × 347 × 161 × 2

這條式子一次同時驗了四件獨立的事：資料段起點找對了（不然解不開）、這確實是 zlib（不然解不開）、檔頭宣告的維度是真的、以及 ushort 等於 2 個位元組。任何一項猜錯，等號都不會成立。用一個容易量的量去交叉檢查一串假設，是判讀未知格式最有效的手法。

這條式子對三個維度的任何排列都成立——153×347×161 和 161×153×347 乘起來一樣大。所以它證明得了「維度是這三個數」，證明不了「哪個數對應哪個軸」。教學網頁「還沒做的事」講的就是這件事，細節見 M-27。驗證通過只代表假設沒被推翻，不代表它是唯一解。

注意 AI 這裡沒有違反「不要寫處理程式」：它只做了判讀（看位元組、驗證一次解壓），沒有產生任何轉檔或處理輸出。「不要寫程式」限制的是產出，不是限制動腦。

2糾錯：證據要能追到位元組與規格

🔴 使用者：把你的判斷依據列出來：檔頭的哪幾個位元組、對應到規格書的哪一段。查不到規格就直接說查不到。

這是整份教材最值得學的一句話。它做了兩件事：把「你怎麼知道」從模糊的敘述逼成可查證的座標；同時預先解除了 AI 說「我不知道」的壓力——「查不到就直接說查不到」等於告訴 AI：老實承認不會被扣分，唬爛才會。

操作原理 · method

M-07算出每個欄位的精確 offset

把檔頭每一段文字對應到「從檔案開頭數起第幾個位元組」。

offset 是量出來的，不是背下來的。做法是在位元組串裡搜尋子字串，回傳的索引就是 offset；子字串長度加上去就是結束位置。這件事值得做的理由不是精確，是可查證性：報告裡寫「offset 438–439 是 78 9c」，任何人都能自己 od 到那個位置去數，不必相信你。把主張釘在別人能重跑的座標上，是這一集第 ② 節真正的方法。

i = b.find(b'define Lattice')
j = b.find(b'\n', i)
print(f'{i}-{j-1}', b[i:j].decode())   # 起訖 offset 與內容一起印

教學網頁那張表的 438 是 fru-F-900054 這個檔的值，不是通則。實際量過 20 個檔，資料段起點分佈在 434–442——因為檔頭是純文字，檔名長度、座標位數不同，檔頭就不一樣長。任何寫死 438 的程式，在另外 19 個檔上都是錯的。位址一律用標記搜尋，不要硬編碼。

純屬推論HxZip = zlib、括號內數字 = 壓縮後長度、ushort = 每體素 2 位元組——全部靠實測反推（招牌位元組、長度相減、解壓後尺寸相符），沒有任何規格背書。
這一段的價值不在於「AI 查到了什麼」，而在於它敢說有四分之三查不到。如果使用者沒加那句「查不到就直接說查不到」，AI 很可能會把推論寫得跟規格一樣肯定。

操作原理 · method

M-08把 78 9c 的每一個位元解出來

依 RFC 1950 §2.2 把兩個位元組拆成五個欄位，逐項對照。

二進位格式常把好幾個資訊擠進同一個位元組，用位元位置區分。取出來的工具只有兩個：遮罩（& ）取特定幾位，位移（>>）把它們挪到最低位。

欄位怎麼取本案的值意思
CMcmf & 0x0f8壓縮方法 = deflate
CINFOcmf >> 47視窗大小 = 2^(7+8) = 32768 位元組
FCHECKflg & 0x1f28湊數用，使 (cmf*256+flg) 被 31 整除
FDICT(flg >> 5) & 10沒有使用預設字典
FLEVELflg >> 62壓縮等級 = 預設

驗算：0x78 = 120，0x9c = 156，120 × 256 + 156 = 30876，30876 ÷ 31 = 996 整除。這就是教學網頁裡「有正式規格佐證的只有兩個位元組」那句話的全部內容——整份判讀裡，只有這兩個位元組能拿一份公開、有編號、任何人查得到的規格來背書。

位元欄位的順序要照規格讀，不要憑直覺。同樣一個位元組，先遮罩再位移和先位移再遮罩結果可能不同。寫完一定要拿規格附的範例值對一次。

M-09把依據分成四個可信度等級

把「我怎麼知道」的每一條依據，按照來源的可查證性分級呈報。

這不是程式，是方法論，但它是這一集最可移植的一招。四級的判準是「別人要花多少力氣才能推翻你」：

等級判準本案的例子
有正式規格公開、有編號、任何人查得到，且直接涵蓋這一點78 9c → RFC 1950 §2.2
只有社群文件有人寫下來但沒有權威地位，或作者自己聲明不是規格define Lattice / BoundingBox 的語意
查不到規格找過了，確實沒有公開文件AmiraMesh 格式本身

要點是：第三級和第四級不是失敗，是誠實的結論。一份判讀報告如果四級都寫成同樣肯定的語氣，讀的人就沒辦法判斷該相信到什麼程度，也沒辦法知道從哪裡開始查證。

分級要在寫結論的時候做，不要事後補。事後補的時候人會傾向把自己推論出來的東西往上調一級。

3請求動作：最小的程式

🟢 使用者：寫一段最小的程式，只做一件事：讀出這 20 個檔案的維度、體素尺寸與資料型別，印成一張表（table.docx）。

「最小」「只做一件事」是很有效的用詞。沒有這兩個限制，AI 很容易順手多做——加個進度條、加個錯誤處理、順便畫個圖——結果變成一個你看不懂也不敢改的東西。

AI 做了什麼寫了 41 行的 read_headers.py。關鍵設計：完全不解壓資料段——維度、體素尺寸、型別三項資訊全都在純文字檔頭裡，只要三個 regex 就能取出。體素尺寸由 (最大值 − 最小值) ÷ (格點數 − 1) 算出。

操作原理 · method

M-10只讀前 8 KB，不解壓資料段

要的三項資訊（維度、體素尺寸、型別）全在純文字檔頭裡，所以只讀檔案開頭一小段。

檔案是可以隨機存取的串流：開檔之後你可以只讀前 N 個位元組就關掉，作業系統不會把整個檔載進記憶體。20 個檔各讀 8 KB 總共 160 KB，跟解壓全部 20 個檔的 400 MB 差了三個數量級。「需要什麼就讀什麼」在資料量大的時候是決定性的差別。

with open(f, 'rb') as fh:
    head = fh.read(8192).decode('latin-1')   # 只讀 8 KB

8192 是有根據的猜測，不是規格保證。本案檔頭最長 442 位元組，8 KB 綽綽有餘，但換一批資料就未必。穩健的寫法是讀到看見資料段標記為止，或至少檢查「這 8 KB 裡有沒有找到 @1」，找不到就報錯而不是靜默給出錯的答案。

M-11用三個 regex 把值取出來

從檔頭文字裡抓出 define Lattice 的三個數、BoundingBox 的六個數、資料型別。

正規表示式是描述字串樣式的小語言：\d+ 是一串數字，() 是「這段我要」，\s+ 是空白。比對引擎掃過文字，把符合樣式的片段連同括號裡的群組交回來。適合用在這種「格式固定、只要幾個值」的場合。

import re
dims = [int(x) for x in re.search(r'define Lattice (\d+) (\d+) (\d+)', head).groups()]
bb   = [float(x) for x in re.search(r'BoundingBox ([-\d.eE+ ]+),', head).group(1).split()]
typ  = re.search(r'Lattice \{ (\w+) Data \}', head).group(1)

為什麼不寫一個完整的 AmiraMesh 剖析器？因為需求只有三個值，而完整剖析器要處理巢狀括號、字串跳脫、各種資料型別，程式碼會多一個數量級，而且每一行都是你之後要維護、要懷疑的東西。這是教材第 ③ 節「最小、只做一件事」在技術層面的意義：能力範圍小的程式，錯的方式也少。

regex 比對失敗時 re.search 回傳 None，直接 .group() 會拋 AttributeError。在批次處理 20 個檔的場合，要嘛檢查 None 並印出是哪個檔，要嘛就讓它拋例外中斷——最糟的是用 try/except 吞掉，得到一張少了幾列的表卻不知道。

M-12由 BoundingBox 算出體素尺寸

檔頭沒有直接寫「一個體素多大」，要從涵蓋範圍與格點數推算。

關鍵在分母是 n−1 還是 n，而這取決於 BoundingBox 量的是哪兩個點：

取樣慣例BoundingBox 的意思體素尺寸n=153 時
節點取樣（本案）第一個與最後一個體素「中心」的座標(max−min)/(n−1)152/152 = 1.000
格子取樣整個影像最外緣的座標(max−min)/n152/153 = 0.993

兩者差 n/(n−1)，在 n=153 時是 0.65%——小到不會讓程式壞掉，大到會讓定量結果錯。本案怎麼判定是節點取樣？用 n−1 算出來三個軸都是 1.000000，用 n 算出來是三個不整齊的數字。「假設 A 讓數字變乾淨、假設 B 不會」是很強的證據，但它是推論不是規格——按 M-09 的分級，這條屬於第四級。

steps = [(hi - lo) / (n - 1)
         for (lo, hi), n in zip(zip(bb[0::2], bb[1::2]), dims)]

這是典型的差一格問題（off-by-one）。籬笆有 10 根柱子只有 9 段間隔——格點數與間隔數永遠差 1。寫這種式子時先問自己：我在數點，還是在數段？

結果：20 個檔案全部是 ushort、體素 1 × 1 × 1 微米，維度則每個檔都不一樣（從 153×347×161 到 842×346×214）。

M-13把結果輸出成摘要表

把 20 列結果寫成一份 Word 表格。

重點不在 docx 這個格式，在於表是程式產生的。手工貼一次表格，上游數字一改它就過期，而且沒有人看得出來它過期了；產生器則是「原始資料 → 表」這條路徑本身被寫了下來，隨時可以重跑。這也是這一集三支程式的共同設計（見 M-24）。

M-14把 20 個檔頭拉齊來比對

把每個檔頭剖析成同樣結構的資料，再逐項比較 20 份之間哪裡不一樣。

比對的前提是先結構化。字串對字串比一定全都不一樣（檔名不同），所以要先把每個檔頭變成一個 dict：{magic, dims, type, order, ...}，然後逐個鍵去比。實作上最順的是分群（等價類）：把 20 個檔按某個鍵的值分堆，堆數等於 1 就是「全部一致」，大於 1 就把每堆的成員列出來。這樣寫的好處是不必事先知道有幾種差異。

from collections import defaultdict
groups = defaultdict(list)
for name, info in headers.items():
    groups[info['order']].append(name)      # 換個鍵就能查別的項目
if len(groups) > 1:
    for value, files in groups.items(): print(len(files), value, files)

今天重跑這一步會得到「20 個檔完全一致」——因為第 ⑤ 節已經把欄位順序統一掉了。原始的兩種順序只存在於 neuron_20.backup/。要重現第 ④ 節的結果，程式要指到備份資料夾。這件事本身就是第 ⑧ 節那一課的實證：抹平之後，沒有備份就真的看不到了。

M-15抓出「欄位順序」這種差異

發現 Parameters 區塊裡六個欄位的內容都一樣，但排列次序有兩種。

這一步能成立，是因為比較的對象選對了：把欄位取出來當成序列（有次序的清單）比，而不是當成集合（只管有沒有）。同一組欄位，當集合看兩群完全相同，當序列看就分成兩堆。選錯了資料結構，這個差異在稽核階段根本不會出現——而它後來被證明是全案唯一的關鍵線索。

M-16自洽性檢查

檢查檔頭裡互相重複記載的資訊有沒有彼此矛盾。

本案的檔頭把同一件事寫了兩次：Content 字串裡有「153x347x161 ushort」，define Lattice 那行也有三個數字；檔名欄位與實際檔名應該對得上；HxZip 括號裡的長度與實際資料段長度應該對得上。兩個獨立來源說同一件事，就可以互相驗證——這是不需要任何外部規格就能做的檢查，而且能抓到「檔案被人改過但只改了一半」這類問題。

m = re.search(r'"(\d+)x(\d+)x(\d+) (\w+)', content_str)
assert [int(x) for x in m.groups()[:3]] == dims
assert m.group(4) == typ

自洽不等於正確。20 個檔的檔頭全部自洽，但它們宣稱的 ushort 跟實際值域還是對不上（第 ⑧ 節）。自洽性檢查抓得到「被改壞」，抓不到「一開始就寫得太寬」。

AI 在這裡犯了一個錯，並且自己抓出來

操作原理 · method

M-17浮點容差誤報：AI 犯的那個錯

第一版檢查把 19 個檔的體素尺寸標成異常，實際上是檢查程式自己的容差設太嚴。

十進位小數大多沒辦法用二進位浮點精確表示，所以浮點運算幾乎永遠帶著微小誤差，用 == 比較兩個算出來的浮點數是錯的做法，要改成「差距小於某個容差」。問題是容差要設多大——這一步的教訓就在這裡：

abs(step - 1.0) < 1e-6      # AI 第一版：太嚴，19 個檔被判異常
abs(step - 1.0) < 1e-4      # 合理：比資料本身的精度寬鬆一級

為什麼 1e-6 太嚴？因為誤差不是來自浮點運算，是來自資料本身：BoundingBox 在檔頭裡只印到 6 位有效數字（例如 -340.636），小數點後第 4 位就被截掉了。拿一個只有 6 位有效數字的輸入去要求 1e-6 的一致性，等於要求比輸入本身還精確的結果。實測 20 個檔的最大偏差是 3.0263e-06——比 1e-6 大，比 1e-4 小，所以在嚴容差下全部翻紅，在合理容差下全部通過。

容差的判準是「資料的精度」，不是「浮點數的精度」。定容差之前先問：我的輸入有幾位有效數字？

這種誤報最危險的地方是它看起來很像真的發現。19 個檔都異常時，正確的直覺是先懷疑檢查程式，而不是先懷疑 19 個檔——當「異常」的比例高到不像異常，通常是判準錯了。AI 這次是靠「前一輪才手算過三個檔都剛好是 1.0」的矛盾察覺的，也就是靠一個獨立來源的舊結果去打臉新結果。

🔍 這是教材裡刻意保留的一段。AI 會犯錯，重點是有沒有辦法自己發現、以及發不發現得了之後老不老實。這次的誤報如果沒抓出來，使用者會以為 19 個檔的體素尺寸都有問題。

5決策：統一欄位順序

🟣 使用者：把欄位順序統一，然後重跑產生 table.docx。
AI 做了什麼動手之前先講了一句反對意見：「這個差異沒有功能影響」——AmiraMesh 的 Parameters 是鍵值結構不是位置結構，程式用欄位名比對，那 5 個檔原本就讀得正確；統一它換到的只是外觀一致。使用者已經下決定，所以 AI 照做，但先複製一份 16 MB 的完整備份再動手。

操作原理 · method

M-18動手前先複製一份完整備份

把整個 neuron_20/ 複製成 neuron_20.backup/ 再開始改。

改寫檔案是不可逆操作：寫入之後原本的位元組就不在磁碟上了。備份把不可逆變成可逆，代價是一份磁碟空間。這裡的成本比是壓倒性的——16 MB 對上「重新培養果蠅、標記、解剖、上共軛焦顯微鏡掃描」的數週工作。值得記住的判準是：備份的成本 vs 重新取得資料的成本，而不是「我覺得應該不會出錯」。

$ cp -a neuron_20 neuron_20.backup     # -a 連時間戳與權限一起保留
$ diff -r neuron_20 neuron_20.backup   # 動手前先確認備份是完整的

備份完要驗一次再動手，不然你可能備份到一半就開始改。另外備份是「留退路」不是「版本控制」——這一集完全沒用 git，但退路確實留住了，第 ⑧ 節就是靠它把線索找回來的。

M-19只重寫 Parameters 區塊

把 5 個檔的檔頭重排，資料段一個位元組都不動。

做法是讀-改-寫：整個檔讀進記憶體，切成「檔頭」與「資料段」兩塊，只重組檔頭那一塊，再把兩塊接起來寫回去。這裡有一個必須想清楚的問題：檔頭長度改變了，資料段的絕對位址就跟著移動，這樣還讀得到嗎？答案是可以，理由有兩個，而這兩個理由都要從格式本身找出來：

  1. 資料段的位置是靠 @1 這個標記找的，不是靠絕對位址。標記往後移，搜尋一樣找得到。
  2. 檔頭裡 HxZip 括號內的 760523 是「壓縮資料的長度」，不是「資料從第幾個位元組開始」。長度不會因為檔頭變長而改變，所以那個數字仍然正確。

如果格式當初設計成「檔頭第 8 個位元組記錄資料段的絕對位址」，這一步就會把檔案改壞——而且是那種解得開、看起來正常、實際上讀到錯位置的壞法。動任何二進位檔之前，先問：這個檔裡有沒有東西記錄著別的東西的位址？

b = path.read_bytes()
i = b.find(b'\n@1\n') + 4
head, data = b[:i], b[i:]              # 資料段原封不動地帶著走
new_head = rebuild_parameters(head)
path.write_bytes(new_head + data)

read_bytes / write_bytes 這種寫法會把整個檔載進記憶體。16 MB 沒問題，幾 GB 的檔就要改成邊讀邊寫。另外寫回去之前先寫到暫存檔再改名，程式中途掛掉才不會留下半個檔——本案沒做這件事，因為有備份。

操作原理 · method

M-20位元組級比對

確認未改動的 15 個檔與備份完全相同，5 個改過的檔其資料段與備份完全相同。

逐位元組比對回答的是「有沒有變」，而且是最強的答案：一個位元組都沒差。雜湊（md5/sha256）是同一件事的壓縮版——比對雜湊值等於比對內容，省了同時開兩份檔的記憶體，代價是理論上存在碰撞（實務上可忽略）。本案只比對資料段那一塊，而不是整個檔，因為檔頭本來就故意改了。驗證要明確界定「哪一塊應該不變」，否則不是漏驗就是誤報。

import hashlib
def data_hash(p):
    b = p.read_bytes(); i = b.find(b'\n@1\n') + 4
    return hashlib.sha256(b[i:]).hexdigest()
assert data_hash(new) == data_hash(backup)

比對通過只證明「沒動到」，不證明「還能用」——這是下一步的事。

M-21真的解壓一次做端到端驗證

把 5 個改寫過的檔實際跑一次 zlib 解壓，並確認解出來的大小仍等於維度相乘乘以 2。

位元組比對驗的是「我沒有破壞它」，解壓驗的是「它整條路走得通」。後者涵蓋前者驗不到的東西：資料段起點找對了、標記沒有被寫壞、檔頭與資料段的接縫沒有多一個或少一個位元組。端到端驗證的定義是：用最終的使用方式跑一次，而不是檢查中間狀態。換到別的場合就是——影片要真的播一次，資料庫備份要真的還原一次。

端到端驗證比較貴（要解壓 400 MB），所以人會想省。省的代價是：所有「看起來沒問題」的檢查都通過，實際打開卻是壞的。折衷是抽樣端到端驗證，但至少要涵蓋所有被改動過的檔。

M-22核對長度宣告：760523 與 760524

檔頭宣告壓縮長度是 760523，從資料段起點數到檔尾是 760524，差 1。

差的那 1 個位元組是檔尾的換行符號（0x0a）。也就是說兩邊在數不同的東西：檔頭數的是「zlib 串流本身有多長」，數到檔尾則是「串流加上結尾換行」。兩者都沒錯，錯的是把它們當成同一個量去比。看到差 1，先問兩邊各自在數什麼，而不是先假設有一邊寫錯了。這跟 M-12 的差一格是同一類問題的兩種面貌。

declared = int(re.search(r'@1\(HxZip,(\d+)\)', head).group(1))
to_eof   = len(b) - start
assert to_eof - declared in (0, 1)      # 允許結尾換行

實測 20 個檔全部是差 1，所以這是這批資料的通則，不是偶然。但它仍然是推論（M-09 第四級）——AmiraMesh 沒有公開規格說「結尾一定有換行」。

操作原理 · method

M-26把 20 個檔全部解壓，統計每個檔的最大值

解壓每個檔的資料段，把位元組流解讀成 16-bit 無號整數陣列，取最大值。

解壓出來的是一長串位元組，要變成數字需要三個約定，全部來自檔頭：每個數字佔幾個位元組（ushort → 2）、有沒有正負號（unsigned）、以及兩個位元組誰排前面（BINARY-LITTLE-ENDIAN → 低位在前）。三個都對，位元組流才會被解讀成正確的數值。端序搞反的話 4095（0x0FFF）會被讀成 65295（0xFF0F）——不會出錯，只會給你錯的答案。

import zlib, numpy as np
raw = zlib.decompress(b[start:])
a = np.frombuffer(raw, dtype='<u2')    # < 小端序, u 無號, 2 兩個位元組
print(a.max(), a.min(), a.size)        # frombuffer 不複製資料，零成本

實測 20 個檔的結果：15 個檔最大值 4095，5 個檔最大值 255，最小值全部是 0。那 5 個正是 TH-F-100051、Tdc2-F-000001、Trh-F-600017、VGlut-F-300388、VGlut-F-600670。

np.frombuffer 回傳的是唯讀視圖，不複製資料——這是它便宜的原因，但要寫入就得先 .copy()。另外一次只處理一個檔就好：20 個檔全部展開約 400 MB，沒必要同時留在記憶體裡。

M-28由最大值反推量化深度

從最大值 4095 判定這是 12-bit 資料，從 255 判定是 8-bit。

n 位元無號整數的最大值是 2ⁿ − 1：255 = 2⁸ − 1，4095 = 2¹² − 1，65535 = 2¹⁶ − 1。看到資料最大值精準地停在這種數字上，最合理的解釋是原始取樣就只有那麼多階，之後被裝進更大的容器（ushort）。共軛焦顯微鏡的相機常見就是 8-bit 或 12-bit，而檔案格式為了對齊都用 16-bit 存。

但這是實測上界，不是證明。嚴格說 4095 只代表「沒有任何體素超過 4095」，12-bit 是最合理的解釋，不是唯一可能——一批真正的 16-bit 資料如果剛好都不亮，也會停在某個值。要更確定可以看數值的分布是否只落在 12-bit 能表示的階上。按 M-09 的分級，這條屬於第四級：純屬推論，但推論得很強。

這件事檔頭完全不會告訴你——20 個檔都寫 ushort。唯一的取得方式是把資料解壓出來實際統計。凡是「宣稱」與「實測」可能不一致的量，都要當成必須實測的量對待。

那 5 個值域只到 255 的檔案，正好就是第 ④ 節找出來的那 5 個欄位順序不同的檔案。一個不多，一個不少。

🔴 這推翻了第 ⑤ 節的判斷。AI 當時說「欄位順序差異沒有功能影響、純屬外觀」——就剖析程式而言那句話是對的，但結論下錯了：欄位順序不是外觀差異，而是兩條不同影像處理管線留下的指紋。同一批來源、同一個工具，寫出不同欄位順序、也寫出不同的強度量化深度。

從 20 個檔裡挑中同樣 5 個的機率是 1/15504 ≈ 0.0065%。這不是巧合。

後果很直接：統一欄位順序，等於把檔頭裡唯一能區分這兩群檔案的線索抹掉了。值域差異藏在壓縮資料裡，不解壓看不到；欄位順序本來是唯一在檔頭層面就能看出來的標記。

✅ 還好第 ⑤ 節有備份。neuron_20.backup/ 裡完整保留著原始欄位順序，這條線索沒有真的消失。「動原始資料前先備份」這個習慣，在這裡實際救了一次。

操作原理 · method

M-29兩群完全重合代表什麼

確認「值域只到 255 的 5 個檔」與「欄位順序不同的 5 個檔」是同一組，並估算這有多不尋常。

從 20 個裡挑 5 個的方法數是組合數：

C(20,5) = 20! / (5! × 15!) = 15504
P(隨機挑中同樣那 5 個) = 1 / 15504 ≈ 6.45e-5 ≈ 0.0065%

所以「兩組毫無關係卻剛好完全重合」的機率是萬分之 0.65。統計上這叫巧合太貴，合理的推論是兩者有共同成因——而共同成因確實找得到：同一條影像處理管線會同時決定寫檔時的欄位順序與相機的量化深度。兩個看似無關的特徵完全共變，通常意味著背後有第三個變數。

分寸要說清楚：這是事後檢定（看到結果才去算機率），所以那個 0.0065% 是描述性的，不是嚴格的假設檢定 p 值——真要做假設檢定，該在看資料之前就決定要檢定什麼。本案的說服力主要來自機制上講得通，機率只是佐證。

重合本身不告訴你因果方向。它沒有證明「欄位順序造成值域不同」，只證明兩者同源。實務上的結論也不是要去解釋順序，而是：做強度比較之前，這 20 個檔不能當成同一批資料處理。

為什麼這件事重要？如果之後要比較這 20 顆神經元的螢光強度，把 0–255 那群和 0–4095 那群直接放在一起比，等於拿不同刻度的尺量東西——低值域那群會系統性地被判定成「比較暗」。而檔頭完全不會告訴你這件事，它 20 個檔都寫 ushort。

操作原理 · method

M-23把改寫程式寫成可重複執行

同一支程式跑第二次不會出錯，也不會把已經整理好的檔再改壞。

這個性質叫冪等性（idempotent）：做一次和做很多次結果相同。做法是程式先判斷「目前是不是已經是目標狀態」，是就跳過。為什麼重要：批次處理常常會中斷（20 個檔跑到第 13 個時出錯），沒有冪等性的話你得先搞清楚哪些已經處理過；有冪等性就直接重跑整批。

if current_order == TARGET_ORDER:
    return 'skip'          # 已經是目標狀態，不動它

冪等的相反不只是「重跑會出錯」，更糟的是「重跑會累積」——例如每跑一次就在檔頭多插一行。設計時問自己：跑第二次會發生什麼？

還沒做的事

  • 軸的對應順序只驗了一半。define Lattice 的三個數字與 BoundingBox 的六個數字是否依 x, y, z 對應，原本完全是沿用慣例的假設——因為已驗證的只有「三維相乘 × 2 = 解壓後大小」，而這個式子對任何軸排列都成立，區分不出順序。製作這份教材時補做了 M-27 說的那件事：真的把影像畫出來看。結果如下——照慣例排出來是一顆神經元，把三個數字擺錯位置就變成條紋。所以「三個數字對應到哪三個軸」這件事現在有證據了；但還是分不出「第一個數是 x 還是 z」，因為 C order 與 Fortran order 兩種慣例只差一個轉置，投影圖看起來一樣。這一條沒有完全解決，只是範圍縮小了。
  • 值域差異尚未處理。第 ⑧ 節只是發現兩群值域。要拿這 20 顆神經元做強度比較之前，得先決定怎麼正規化。
  • 欄位順序要不要還原還沒決定。備份完整，兩個方向都走得通。

PART 49 個核心教訓

看完整段真實過程，把精髓濃縮成這 9 條帶走——每條都對應你剛剛讀到的某個段落。

① 先判讀，再動手——「先不要寫程式」是一句好指令

使用者第一句話就禁止 AI 寫任何處理程式。這擋掉了最常見的失敗模式：還沒搞懂資料格式就開始寫轉檔程式，寫出來的東西看似能跑，實際在瞎猜。判讀階段和實作階段要分開。

② 把「你怎麼知道」逼成可查證的座標

「檔頭的哪幾個位元組、對應規格書的哪一段」——這句話把回答從敘述層次拉到證據層次。AI 因此做了完整位元組傾印，也因此發現自己原本的說法有四分之三沒有規格依據。你問問題的精確度，決定你得到答案的精確度。

③ 先解除「不知道」的壓力，才問得到實話

「查不到規格就直接說查不到」是一句授權。有了它，AI 才會把依據分成「有規格／社群文件／純屬推論」四級誠實呈報，而不是把猜測寫得跟事實一樣肯定。這句話幾乎可以加在任何你要求 AI 查證的場合。

④ 「最小」「只做一件事」是有效的限制詞

沒有這兩個詞，AI 很容易順手加功能，最後給你一個你看不懂也不敢改的程式。本案的 read_headers.py 只有 41 行，而且刻意不解壓資料段——因為要的三項資訊都在純文字檔頭裡。

⑤ 把「發現問題」和「處理問題」拆成兩個回合

「如果有，先不要修，列出來」——這樣你才看得見問題本身，才輪得到你決定要不要動、怎麼動。如果讓 AI 一口氣發現並修掉，你會永遠不知道原本長什麼樣。

⑥ AI 該先說反對意見，然後照你的決定做

使用者說要統一欄位順序時，AI 先講明「這沒有功能影響、只是外觀」，然後照做，但先備份。這是正確的分工：AI 負責讓你知道代價，你負責決定。（附帶一提，AI 那句「沒有功能影響」後來被證明是看走眼——見第 ⑨ 條。）

⑦ 動原始資料前先備份，而且要端到端驗證

16 MB 的備份很便宜，重新採樣一批共軛焦影像很貴。驗證也不能只比對位元組——比對只能證明「沒動到」，真的解壓出來才能證明「還能用」。本案兩件事都做了，而第 ⑧ 節證明備份確實派上用場。

⑧ 紀錄要包含自己犯的錯

AI 在稽核時把 19 個檔誤判為體素異常（自己的浮點容差設太緊），發現後主動更正，並把這次誤報寫進正式報告。一份看起來完全順利的紀錄，通常是漏寫了什麼。

⑨ 「沒有功能影響」不等於「沒有意義」——這一集最貴的一課

欄位順序差異對程式解析毫無影響，所以被當成外觀問題統一掉了。事後才發現：那 5 個檔正好也是強度值域只到 255 的那 5 個（機率 1/15504）。它不是外觀差異，是兩條處理管線的指紋。當你發現一個「無害的不一致」，先問它為什麼存在，再決定要不要抹平。
