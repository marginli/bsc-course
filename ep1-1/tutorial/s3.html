3請求動作：最小的程式

使用者發言的五種顏色🟢 請求動作🔵 問問題🟣 關鍵決策🟡 中斷 / 踩剎車🔴 設計回饋 / 糾錯完整說明 →
🟢 使用者：寫一段最小的程式，只做一件事：讀出這 20 個檔案的維度、體素尺寸與資料型別，印成一張表（table.docx）。

「最小」「只做一件事」是很有效的用詞。沒有這兩個限制，AI 很容易順手多做——加個進度條、加個錯誤處理、順便畫個圖——結果變成一個你看不懂也不敢改的東西。

AI 做了什麼寫了 41 行的 read_headers.py。關鍵設計：完全不解壓資料段——維度、體素尺寸、型別三項資訊全都在純文字檔頭裡，只要三個 regex 就能取出。體素尺寸由 (最大值 − 最小值) ÷ (格點數 − 1) 算出。

「操作原理」（四個欄位，點一下展開）——不寫程式的話整段可以跳過。

操作原理 · method

M-10只讀前 8 KB，不解壓資料段

要的三項資訊（維度、體素尺寸、型別）全在純文字檔頭裡，所以只讀檔案開頭一小段。

檔案是可以隨機存取的串流：開檔之後你可以只讀前 N 個位元組就關掉，作業系統不會把整個檔載進記憶體。20 個檔各讀 8 KB 總共 160 KB，跟解壓全部 20 個檔的 400 MB 差了三個數量級。「需要什麼就讀什麼」在資料量大的時候是決定性的差別。

with open(f, 'rb') as fh:
    head = fh.read(8192).decode('latin-1')   # 只讀 8 KB
← 可左右滑動 →

8192 是有根據的猜測，不是規格保證。本案檔頭最長 442 位元組，8 KB 綽綽有餘，但換一批資料就未必。穩健的寫法是讀到看見資料段標記為止，或至少檢查「這 8 KB 裡有沒有找到 @1」，找不到就報錯而不是靜默給出錯的答案。

M-11用三個 regex 把值取出來

從檔頭文字裡抓出 define Lattice 的三個數、BoundingBox 的六個數、資料型別。

正規表示式是描述字串樣式的小語言：\d+ 是一串數字，() 是「這段我要」，\s+ 是空白。比對引擎掃過文字，把符合樣式的片段連同括號裡的群組交回來。適合用在這種「格式固定、只要幾個值」的場合。

import re
dims = [int(x) for x in re.search(r'define Lattice (\d+) (\d+) (\d+)', head).groups()]
bb   = [float(x) for x in re.search(r'BoundingBox ([-\d.eE+ ]+),', head).group(1).split()]
typ  = re.search(r'Lattice \{ (\w+) Data \}', head).group(1)
← 可左右滑動 →

為什麼不寫一個完整的 AmiraMesh 剖析器？因為需求只有三個值，而完整剖析器要處理巢狀括號、字串跳脫、各種資料型別，程式碼會多一個數量級，而且每一行都是你之後要維護、要懷疑的東西。這是教材第 ③ 節「最小、只做一件事」在技術層面的意義：能力範圍小的程式，錯的方式也少。

regex 比對失敗時 re.search 回傳 None，直接 .group() 會拋 AttributeError。在批次處理 20 個檔的場合，要嘛檢查 None 並印出是哪個檔，要嘛就讓它拋例外中斷——最糟的是用 try/except 吞掉，得到一張少了幾列的表卻不知道。

M-12由 BoundingBox 算出體素尺寸

檔頭沒有直接寫「一個體素多大」，要從涵蓋範圍與格點數推算。

關鍵在分母是 n−1 還是 n，而這取決於 BoundingBox 量的是哪兩個點：

取樣慣例BoundingBox 的意思體素尺寸n=153 時
節點取樣（本案）第一個與最後一個體素「中心」的座標(max−min)/(n−1)152/152 = 1.000
格子取樣整個影像最外緣的座標(max−min)/n152/153 = 0.993

兩者差 n/(n−1)，在 n=153 時是 0.65%——小到不會讓程式壞掉，大到會讓定量結果錯。本案怎麼判定是節點取樣？用 n−1 算出來三個軸都是 1.000000，用 n 算出來是三個不整齊的數字。「假設 A 讓數字變乾淨、假設 B 不會」是很強的證據，但它是推論不是規格——按 M-09 的分級，這條屬於第四級。

steps = [(hi - lo) / (n - 1)
         for (lo, hi), n in zip(zip(bb[0::2], bb[1::2]), dims)]
← 可左右滑動 →

這是典型的差一格問題（off-by-one）。籬笆有 10 根柱子只有 9 段間隔——格點數與間隔數永遠差 1。寫這種式子時先問自己：我在數點，還是在數段？

結果：20 個檔案全部是 ushort、體素 1 × 1 × 1 微米，維度則每個檔都不一樣（從 153×347×161 到 842×346×214）。

M-13把結果輸出成摘要表

把 20 列結果寫成一份 Word 表格。

重點不在 docx 這個格式，在於表是程式產生的。手工貼一次表格，上游數字一改它就過期，而且沒有人看得出來它過期了；產生器則是「原始資料 → 表」這條路徑本身被寫了下來，隨時可以重跑。這也是這一集三支程式的共同設計（見 M-24）。

from docx import Document
doc = Document(); t = doc.add_table(rows=1, cols=5); t.style = 'Table Grid'
for c, name in zip(t.rows[0].cells, ['檔名','維度','體素尺寸','型別','大小']):
    c.text = name
for r in rows:
    for c, v in zip(t.add_row().cells, r): c.text = str(v)
doc.save('table.docx')
← 可左右滑動 →

產生器要能重複執行且輸出一致。如果表裡放了執行時間、隨機排序、或字典的迭代順序，兩次跑出來的檔就會不一樣，之後想比對「有沒有變」時會很痛苦。

⚠️ 這裡有個伏筆：「資料型別 ushort」是檔頭宣稱的，不是實測的。這個區別在 第 ⑧ 節會變得很重要。
