操作原理 · method

M-23把改寫程式寫成可重複執行

同一支程式跑第二次不會出錯，也不會把已經整理好的檔再改壞。

這個性質叫冪等性（idempotent）：做一次和做很多次結果相同。做法是程式先判斷「目前是不是已經是目標狀態」，是就跳過。為什麼重要：批次處理常常會中斷（20 個檔跑到第 13 個時出錯），沒有冪等性的話你得先搞清楚哪些已經處理過；有冪等性就直接重跑整批。

if current_order == TARGET_ORDER:
    return 'skip'          # 已經是目標狀態，不動它

冪等的相反不只是「重跑會出錯」，更糟的是「重跑會累積」——例如每跑一次就在檔頭多插一行。設計時問自己：跑第二次會發生什麼？

還沒做的事

  • 軸的對應順序只驗了一半。define Lattice 的三個數字與 BoundingBox 的六個數字是否依 x, y, z 對應，原本完全是沿用慣例的假設——因為已驗證的只有「三維相乘 × 2 = 解壓後大小」，而這個式子對任何軸排列都成立，區分不出順序。製作這份教材時補做了 M-27 說的那件事：真的把影像畫出來看。結果如下——照慣例排出來是一顆神經元，把三個數字擺錯位置就變成條紋。所以「三個數字對應到哪三個軸」這件事現在有證據了；但還是分不出「第一個數是 x 還是 z」，因為 C order 與 Fortran order 兩種慣例只差一個轉置，投影圖看起來一樣。這一條沒有完全解決，只是範圍縮小了。
  • 值域差異尚未處理。第 ⑧ 節只是發現兩群值域。要拿這 20 顆神經元做強度比較之前，得先決定怎麼正規化。
  • 欄位順序要不要還原還沒決定。備份完整，兩個方向都走得通。

操作原理 · method

M-27reshape 成 3D 與軸順序問題

把一維陣列排成 (153, 347, 161) 的立體影像——教材原本明講「還沒驗證」，後來補做了。

一維變三維要知道哪個軸在記憶體裡變化最快。兩種主要慣例：

慣例誰在用reshape 寫法（x 最快）
C order（列優先）C、Python/NumPy 預設a.reshape(nz, ny, nx) → 索引 [z][y][x]
Fortran order（行優先）Fortran、MATLAB、多數科學影像格式a.reshape(nx, ny, nz, order='F')

麻煩的是：任何一種排法都不會報錯，因為元素總數一樣。M-06 的尺寸恆等式對三個維度的任何排列都成立，所以它區分不出順序。唯一能確認的方法是把影像畫出來看——排錯的話會看到條紋狀的亂訊，而不是神經元。教材原本誠實地把這件事列在「還沒做的事」；製作這一版時真的畫了，對照圖就在〈本次成果〉的「還沒做的事」那一段。結論是：三個數字對應到哪三個軸，畫出來就分得出來；但 C order 與 Fortran order 只差一個轉置，投影圖分不出來，所以那一半仍然沒有證據——「還沒做的事」那一條縮小了範圍，沒有消失。

這是「驗證通過 ≠ 唯一解」最具體的例子（見 〈前置知識〉1-5）。一個檢查如果對所有候選答案都成立，它的資訊量是零——設計驗證時要問：這個檢查能不能把錯的假設篩掉？
