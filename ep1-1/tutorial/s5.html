🟣 使用者：把欄位順序統一，然後重跑產生 table.docx。
AI 做了什麼動手之前先講了一句反對意見：「這個差異沒有功能影響」——AmiraMesh 的 Parameters 是鍵值結構不是位置結構，程式用欄位名比對，那 5 個檔原本就讀得正確；統一它換到的只是外觀一致。使用者已經下決定，所以 AI 照做，但先複製一份 16 MB 的完整備份再動手。

下面的「操作原理」是給想自己動手寫程式的人看的，四個欄位預設收著；整段跳過不影響後面的閱讀。

操作原理 · method

M-18動手前先複製一份完整備份

把整個 neuron_20/ 複製成 neuron_20.backup/ 再開始改。

改寫檔案是不可逆操作：寫入之後原本的位元組就不在磁碟上了。備份把不可逆變成可逆，代價是一份磁碟空間。這裡的成本比是壓倒性的——16 MB 對上「重新培養果蠅、標記、解剖、上共軛焦顯微鏡掃描」的數週工作。值得記住的判準是：備份的成本 vs 重新取得資料的成本，而不是「我覺得應該不會出錯」。

$ cp -a neuron_20 neuron_20.backup     # -a 連時間戳與權限一起保留
$ diff -r neuron_20 neuron_20.backup   # 動手前先確認備份是完整的

備份完要驗一次再動手，不然你可能備份到一半就開始改。另外備份是「留退路」不是「版本控制」——這一集完全沒用 git，但退路確實留住了，第 ⑧ 段就是靠它把線索找回來的。

M-19只重寫 Parameters 區塊

把 5 個檔的檔頭重排，資料段一個位元組都不動。

做法是讀-改-寫：整個檔讀進記憶體，切成「檔頭」與「資料段」兩塊，只重組檔頭那一塊，再把兩塊接起來寫回去。這裡有一個必須想清楚的問題：檔頭長度改變了，資料段的絕對位址就跟著移動，這樣還讀得到嗎？答案是可以，理由有兩個，而這兩個理由都要從格式本身找出來：

  1. 資料段的位置是靠 @1 這個標記找的，不是靠絕對位址。標記往後移，搜尋一樣找得到。
  2. 檔頭裡 HxZip 括號內的 760523 是「壓縮資料的長度」，不是「資料從第幾個位元組開始」。長度不會因為檔頭變長而改變，所以那個數字仍然正確。

如果格式當初設計成「檔頭第 8 個位元組記錄資料段的絕對位址」，這一步就會把檔案改壞——而且是那種解得開、看起來正常、實際上讀到錯位置的壞法。動任何二進位檔之前，先問：這個檔裡有沒有東西記錄著別的東西的位址？

b = path.read_bytes()
i = b.find(b'\n@1\n') + 4
head, data = b[:i], b[i:]              # 資料段原封不動地帶著走
new_head = rebuild_parameters(head)
path.write_bytes(new_head + data)

read_bytes / write_bytes 這種寫法會把整個檔載進記憶體。16 MB 沒問題，幾 GB 的檔就要改成邊讀邊寫。另外寫回去之前先寫到暫存檔再改名，程式中途掛掉才不會留下半個檔——本案沒做這件事，因為有備份。

然後是驗證。改寫原始研究資料，光「看起來沒壞」是不夠的：

檢查結果
未改動的 15 檔 vs 備份位元組完全相同
5 個重寫檔的壓縮資料段 vs 備份位元組完全相同（@1 之後一個位元組都沒動）
5 個重寫檔實際跑 zlib 解壓成功，解出大小 = 維度相乘 × 2，相符
壓縮長度宣告 vs 實際仍然一致
欄位順序種類由 2 種降為 1 種
第 3 項是關鍵：真的把資料解壓出來，而不是只比對位元組。比對位元組只能證明「沒動到」，解壓才能證明「還能用」。

操作原理 · method

M-20位元組級比對

確認未改動的 15 個檔與備份完全相同，5 個改過的檔其資料段與備份完全相同。

逐位元組比對回答的是「有沒有變」，而且是最強的答案：一個位元組都沒差。雜湊（md5/sha256）是同一件事的壓縮版——比對雜湊值等於比對內容，省了同時開兩份檔的記憶體，代價是理論上存在碰撞（實務上可忽略）。本案只比對資料段那一塊，而不是整個檔，因為檔頭本來就故意改了。驗證要明確界定「哪一塊應該不變」，否則不是漏驗就是誤報。

import hashlib
def data_hash(p):
    b = p.read_bytes(); i = b.find(b'\n@1\n') + 4
    return hashlib.sha256(b[i:]).hexdigest()
assert data_hash(new) == data_hash(backup)

比對通過只證明「沒動到」，不證明「還能用」——這是下一步的事。

M-21真的解壓一次做端到端驗證

把 5 個改寫過的檔實際跑一次 zlib 解壓，並確認解出來的大小仍等於維度相乘乘以 2。

位元組比對驗的是「我沒有破壞它」，解壓驗的是「它整條路走得通」。後者涵蓋前者驗不到的東西：資料段起點找對了、標記沒有被寫壞、檔頭與資料段的接縫沒有多一個或少一個位元組。端到端驗證的定義是：用最終的使用方式跑一次，而不是檢查中間狀態。換到別的場合就是——影片要真的播一次，資料庫備份要真的還原一次。

端到端驗證比較貴（要解壓 400 MB），所以人會想省。省的代價是：所有「看起來沒問題」的檢查都通過，實際打開卻是壞的。折衷是抽樣端到端驗證，但至少要涵蓋所有被改動過的檔。

M-22核對長度宣告：760523 與 760524

檔頭宣告壓縮長度是 760523，從資料段起點數到檔尾是 760524，差 1。

差的那 1 個位元組是檔尾的換行符號（0x0a）。也就是說兩邊在數不同的東西：檔頭數的是「zlib 串流本身有多長」，數到檔尾則是「串流加上結尾換行」。兩者都沒錯，錯的是把它們當成同一個量去比。看到差 1，先問兩邊各自在數什麼，而不是先假設有一邊寫錯了。這跟 M-12 的差一格是同一類問題的兩種面貌。

declared = int(re.search(r'@1\(HxZip,(\d+)\)', head).group(1))
to_eof   = len(b) - start
assert to_eof - declared in (0, 1)      # 允許結尾換行

實測 20 個檔全部是差 1，所以這是這批資料的通則，不是偶然。但它仍然是推論（M-09 第四級）——AmiraMesh 沒有公開規格說「結尾一定有換行」。
